    CoreFlow Spec Kit

    Behavior Specification — Todo Application

    Version 1.0 Status: Stable Scope: Vanilla JS · DOM-as-state
    ℹ️
    How to use this spec
    Every rule has a unique ID (e.g. CF-ADD-01). The reference implementation annotates each rule in comments. Use the IDs to link code, tests, and checklist items.

    §1 Terminology

    TermDefinition
    Todo itemA text string representing a task, persisted as a DOM element with associated state.
    PendingA todo item whose data-completed attribute is "false".
    CompletedA todo item whose data-completed attribute is "true".
    DOM-as-stateThe list DOM is the single source of truth; no separate JavaScript array mirrors it.
    TrimRemoving leading and trailing whitespace via String.prototype.trim().
    InvariantA condition that must hold at all times, regardless of user actions.

    §2 Action Flows

    CF-ADDAdd Todo5 rules
    Preconditions
    The input field is rendered and not disabled.
    The user has focused the input field (via click or tab).
    Trigger:

    User presses Enter or activates the "Add" button.

    Normal flow:
    1
    CF-ADD-01 — The system trims the raw input value (removes leading/trailing whitespace).
    2
    CF-ADD-02 — If the trimmed text is empty (length === 0), an inline error is shown: "Todo text cannot be empty." The form is not submitted.
    3
    CF-ADD-03 — If the trimmed text exceeds 200 characters, an inline error is shown: "Todo text cannot exceed 200 characters." The form is not submitted.
    4
    The system creates a new todo item DOM element using the trimmed text. Initial state: Pending (data-completed="false").
    5
    CF-ADD-05 — The system appends the new item to the end of the list (not prepend).
    6
    CF-ADD-04 — The system clears the input field and returns focus to it.
    7
    Counter and empty-state visibility are updated (CF-UI-01, CF-UI-02).
    Postconditions
    New list item with trimmed text is visible at the bottom of the list.
    Input field is empty and focused.
    No error message is displayed.
    CF-TOGToggle Completion3 rules
    Preconditions
    At least one todo item exists in the list.
    Trigger:

    User clicks the checkbox or the todo text label of a specific item.

    Normal flow:
    1
    CF-TOG-01 — The system toggles the completion state of exactly and only the target item. No other items are affected.
    2
    CF-TOG-02 — The visual state updates synchronously: completed items show a checked circle and struck-through text.
    3
    CF-TOG-03 — The action is fully reversible: toggling a completed item returns it to pending, and vice versa.
    Postconditions
    Target item's data-completed is the opposite of its prior value.
    All other items retain their prior states unchanged.
    CF-DELDelete Todo2 rules
    Trigger:

    User activates the "×" delete button on a specific item.

    1
    CF-DEL-01 — The system removes from the DOM exactly and only the item associated with the activated delete button.
    2
    CF-DEL-02 — No other items are affected. Items above and below retain their positions and states.
    3
    Counter and empty-state are updated (CF-UI-01, CF-UI-02).
    CF-UIUI State Management3 rules
    1
    CF-UI-01 (Empty State) — The empty-state element MUST be visible if and only if the list contains zero items.
    2
    CF-UI-02 (Counter) — The footer counter MUST display "N of M completed". When all items are completed, the counter uses a success visual treatment.
    3
    CF-UI-03 (Accessibility) — All interactive controls MUST be operable via keyboard. All inputs and controls MUST have programmatic labels. Live regions MUST announce list changes.

    §3 System Invariants

    These conditions must hold at all times:

    • The data-completed attribute of every item is exactly "true" or "false" — no other values.
    • The visible text of each item exactly matches its trimmed creation input — no extra whitespace.
    • The total item count displayed in the counter equals the number of .todo-item elements in the DOM.
    • No item is both visually struck-through and has data-completed="false" (visual and data states are always in sync).
    • The empty state is visible if and only if zero .todo-item elements exist.
    • The input field is never pre-populated with a previously submitted value after a successful add.

    §4 Non-Goals (Explicitly Out of Scope)

    FeatureReason excluded from v1
    Persistence (localStorage / server)DOM-as-state exercise. Persistence is a separate concern.
    Filtering (All / Active / Completed)Kept minimal to focus on core CRUD and state management.
    Drag-to-reorderRequires event handling beyond the module's scope.
    Inline editing of existing itemsDeferred to an advanced extension exercise.
    Duplicate detectionPolicy decision deferred; both allow and warn are reasonable.
    Animations / transitionsVisual polish is secondary to behavioral correctness.
    Framework-specific patternsVanilla JS fundamentals only in v1.

    Instructor Guide

    90-min lab session Vanilla JS Beginner–Intermediate

    🎯 Learning Objectives

    After completing this module, students will be able to:

    1. Read and interpret a formal UI behavior specification, translating spec rules into testable acceptance criteria.
    2. Implement DOM manipulation using vanilla JavaScript — creating, reading, updating, and deleting elements without a framework.
    3. Apply the DOM-as-state pattern: use the DOM as the single source of truth rather than maintaining a parallel JavaScript data structure.
    4. Handle edge cases explicitly — empty input, whitespace-only input, boundary conditions — as specified in a written spec.
    5. Write accessible interactive UI using ARIA attributes, keyboard navigation, and live regions.

    📋 Prerequisites

    Required
    • HTML structure and semantic elements
    • JavaScript variables, functions, conditionals
    • Basic DOM querying (querySelector)
    • Event listeners (addEventListener)
    Helpful but not required
    • CSS specificity and custom properties
    • HTML forms and validation
    • ARIA basics and accessibility

    ⏱ 90-Minute Lesson Plan

    0:00 – 0:10
    Open with the problem (10 min)
    Show two "todo apps" side-by-side — one that accepts blank todos, one that doesn't. Ask: "Which is correct?" Introduce the spec as the answer. Without a spec, "correct" is undefined.
    0:10 – 0:25
    Walk through the Spec Doc (15 min)
    Read §2 Action Flows together. Have students highlight preconditions vs. postconditions in two colors. Discuss: "What would happen if we skipped CF-ADD-01?" Emphasize that spec IDs make communication unambiguous.
    0:25 – 0:40
    Live App exploration (15 min)
    Open the Live App tab. Demo each action. Have students try to break it — submit empty, submit spaces, type 200+ chars. Reference the spec rule that prevents each bad state.
    0:40 – 0:70
    Exercise A — Debug (30 min)
    Students work individually or in pairs. They identify each bug, name the spec rule it violates, and write the fix. Circulate and coach. Avoid giving direct answers — ask "What does CF-ADD-02 say should happen?"
    0:70 – 0:80
    Debrief Exercise A (10 min)
    Review each bug as a class. Highlight the "Toggle All" bug (Bug 3) — a classic misuse of querySelectorAll vs. targeting the specific element.
    0:80 – 0:90
    Introduce Exercise B + wrap-up (10 min)
    Introduce "Clear Completed". Walk through writing a mini-spec before coding. Assign as homework. Close by asking: "What's one thing you'd add to the spec?"

    💬 Discussion Questions

    1. The spec says new items are appended (CF-ADD-05). What trade-offs would "prepend" vs. "append" create for a shared grocery list vs. a work task tracker?
    2. CF-ADD-01 requires trimming whitespace. Are there scenarios where you would not want to trim? (Hint: consider a code snippet manager.)
    3. The spec is silent on duplicate todos. Write a one-sentence rule for your preferred behavior and a one-sentence rule for the opposite. Which creates more user surprise?
    4. DOM-as-state means the DOM holds all data. What are the risks if a user edits the DOM via Dev Tools? How would you mitigate this in a production app?
    5. The spec requires keyboard accessibility (CF-UI-03). How would a blind user test CF-TOG-01 — that toggle only affects the target item?

    ⚠️ Common Student Mistakes

    MistakeSpec violationCoaching hint
    Using .value.length === 0 without trimmingCF-ADD-01/02"What does the user see if they press spacebar 5 times and hit Enter?"
    Forgetting to clear the input after addCF-ADD-04"Read the postconditions for CF-ADD. What state must the input be in?"
    Using querySelectorAll to toggle instead of the specific itemCF-TOG-01"How many elements does querySelectorAll return? Is that what the spec says?"
    Deleting list.firstChild instead of the clicked itemCF-DEL-01/02"What does the user expect when they click delete on the third item?"
    Not updating counter/empty state after mutationsCF-UI-01/02"Is the counter displaying the current state? How does the spec define its invariant?"
    Using innerHTML with unsanitized user inputSecurity (XSS)"What happens if the user types <script>alert(1)</script>?"

    Exercise B · Feature Extension

    Add "Clear Completed"

    Extend the todo app with a scoped new feature. Write a mini-spec first, then implement it. The feature must not break any existing spec rules.

    📋 Feature Request

    💬
    User story
    "As a user with multiple completed tasks, I want to remove all completed items at once so that I can declutter my list without deleting each one individually."

    Feature name: Clear Completed

    Trigger: A "Clear completed" button in the todo app footer.

    Constraint: The button must not appear when there are zero completed items. It must not affect pending items.

    Step 1 — Write the Mini-Spec First

    Before touching the code, write a spec entry using the same format as §2. Include:

    • A unique spec ID (suggest: CF-CLR)
    • Preconditions (when should the button be visible?)
    • Trigger and normal flow (numbered steps)
    • Postconditions and one invariant
    📝
    Write your spec on paper or a separate document. Do not start coding until it has been reviewed by your partner or instructor.

    Step 2 — Acceptance Criteria

    #CriterionHow to verify
    AC-1"Clear completed" button is not visible when no items are completed.Add 2 todos, don't check any. Button should be hidden.
    AC-2Button appears when at least one item is completed.Check one item. Button should become visible.
    AC-3Clicking removes all completed items.Complete 3 of 5 items, click button. 2 pending items remain.
    AC-4Pending items are not affected.After clear, all remaining items have data-completed="false".
    AC-5Counter (CF-UI-02) updates correctly after clear.Counter should show "0 of 2 completed" after AC-3 scenario.
    AC-6Empty state (CF-UI-01) shows if all items were completed and cleared.Complete all items, click clear. Empty state should appear.
    AC-7Button is keyboard-accessible.Tab to the button and press Enter. Same result as mouse click.
    AC-8No existing spec rules are broken.Run through all existing behaviors after adding the feature.

    Step 3 — Implementation Hints

    Add the button to the todo footer. Give it id="clear-done-btn" and start with the hidden attribute. In your updateUI() function, toggle hidden based on whether any [data-completed="true"] items exist.

    const completed = document.querySelectorAll('.todo-item[data-completed="true"]'); completed.forEach(item => item.remove()); updateUI();
    const clearBtn = document.getElementById('clear-done-btn'); // Show button only when there are completed items clearBtn.hidden = completed.length === 0;

    🚀 Bonus Challenges

    1. Undo delete: After deleting an item, show a "Undo" toast for 5 seconds. Clicking Undo restores the item to its previous position and state.
    2. Item count badge: Display pending count in the browser tab title (e.g. (3) My Todos). Spec the format and when the number is omitted.
    3. Keyboard shortcut: Ctrl+Z / Cmd+Z undoes the last add or delete. Spec behavior for multiple consecutive undos.
    4. Filter row: Add "All", "Active", "Completed" filters. Spec the interaction between filters and the empty state message.
